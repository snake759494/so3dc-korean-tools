# Star Ocean 3 DC 폰트 이미지 한자 매핑 보고서

작성일: 2026-07-14  
대상: Disc 1에서 추출한 `so3mclib` 폰트 컨테이너 7,786개  
검증 범위: 24×24 및 32×32 글리프 이미지, 원본 메시지 문맥, 전체 매핑·대사 JSON 재생성  
에뮬레이터: 실행하지 않음

## 최종 결과

| 글리프 크기 | 조사한 고유 글리프 | 한자 계열 비트맵 형태 | 비고 |
|---|---:|---:|---|
| 24×24 | 4,423 | 3,904 | `〇` 1형태 포함 |
| 32×32 | 623 | 412 | 비한자 판정 213개 전수 문맥 검수, 미해결 0 |
| 합계 | 5,046 | 4,316 | 서로 다른 Unicode 한자 계열 문자는 2,272자 |

여기서 “형태”는 글꼴·크기·안티앨리어싱이 다른 비트맵을 각각 센 값이다. 따라서 같은 Unicode 문자라도 서로 다른 비트맵이면 별도 항목이다. 매핑 키는 atlas 순번이 바뀌어도 안전하도록 다음 형식을 사용한다.

```text
<width>x<height>:<raw decoded glyph bitmap SHA-256>
```

한자 계열 4,316형태의 근거 구성은 다음과 같다.

- Windows 일본어 OCR 3종 만장일치: 3,974
- Windows OCR 2/3 + MS Gothic CP932 템플릿 top-5 교차검증: 103
- 기존 직접·동일 비트맵 근거: 62
- 사람이 atlas와 실제 메시지 문맥으로 확정: 177
- 라벨 충돌: 0

## 인식 및 검수 방법

1. 모든 `so3mclib`의 원시 4bpp 글리프를 해독하고 geometry+SHA-256으로 고유 형태를 만들었다.
2. 24px atlas에서는 전역 글꼴과 겹치지 않는 local-added U0123–U1269, 4,423개를 순서대로 처리했다.
3. 32px atlas에서는 U0000–U026E, 623개 전체를 순서대로 처리했다.
4. Windows 일본어 OCR에 bicubic gray, nearest gray, binary nearest 세 변형을 각각 입력해 투표했다.
5. CP932 한자 6,682자를 MS Gothic으로 렌더링한 템플릿 top-5와 교차검증했다.
6. 기존 직접 매핑으로 24px 64/64, 32px 인식 가능 표본 4/4가 일치하는지 확인했다.
7. OCR 비한자 판정도 실제 메시지의 glyph code 문맥으로 역추적해 동형자 누락을 찾았다.
8. 확정 라벨을 실제 184,141개 local/special 슬롯에 다시 적용하고, 원본 메시지 183,065개를 재디코드했다.

## 중요 수동 교정

24px 비한자 OCR 후보 520개를 감사해 다음 9형태를 추가했다.

- U0146 `口`: `端麗辛口`, `一口大`, `口の中`
- U030C `二`: `二本一組`, `二足歩行`, `二度`, `二段技`
- U08BA `夕`: `夕暮れの半刻`
- U0D19 `二`: `二酸化硫黄物語`
- U0D78 `夕`: `明日の夕方`, `夕暮れの半刻`
- U0E28 `〇`: `〇月×日`
- U1152 `一`: `一の書～`
- U1178 `二`: `二の書～`
- U11BA `力`: `内に秘めたる力を解き放つは何者ぞ`

32px 623개는 내장 메시지 1,220개와 전수 대조했다.

- 숨은 한자: U0071 `二`, U0091 `口`, U00A8 `夕`
- 한자 오분류 제거: U0090 `工` → `エ` (`戦闘エフェクト`)
- 자체 교정: U01CF `奧` → `奥`
- 신·구자체를 별도 보존: `真/眞`, `澤/沢`, `富/冨`, `崎/﨑`, `斉/齊`, `寿/壽`

24px에서 OCR이 한자로 본 채 남아 있던 14형태도 다시 확인했다. 이들은 `α`, `β`, Latin 문자·숫자·블록 UI 기호 등이며 실제 한자가 아니므로 매핑하지 않았다. review queue의 215/68건은 템플릿 점수가 높았던 ASCII·가나·기호까지 포함하므로 “미확인 한자 수”가 아니다. 최종적으로 남은 실제 한자 후보는 0이다.

## 재현성 검증

최종 파이프라인을 두 번 실행해 `font_mapping_table.json` SHA-256이 다음 값으로 고정되는 것을 확인했다.

```text
5fdaeb577e67c4a1fa13b743f1301a21fcd71ca66c8d2c4409b15f846dd293eb
```

24px·32px ordered JSON에 기록된 `preexisting_mapping` 해시도 위 현재 파일과 일치한다. 검증 도구는 다음 항목을 검사한다.

현재 provenance의 `path` 값은 분석 PC의 절대 경로다. 파일 동일성은 함께 기록한 SHA-256으로 검증되지만, 공개 릴리스에 넣을 때는 경로만 저장소 상대 경로로 정규화하는 편이 이식성이 좋다.

- atlas CSV union 순서와 ordered JSON 전행 SHA 일치
- geometry별 라벨과 결합 라벨의 정확한 합집합
- compact 한자 JSON이 ordered JSON의 한자 행만 순서대로 보존하는지 확인
- 모든 라벨 키가 실제 슬롯에 존재하고 같은 Unicode로 적용됐는지 확인
- 수동 SHA prefix의 geometry 내 1:1 유일성
- font OCR 충돌 0 및 대사 JSON 구조

```powershell
python work\font_ocr\validate_font_ocr_outputs.py
```
